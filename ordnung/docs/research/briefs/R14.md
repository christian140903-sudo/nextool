# R14 — Adversariale Prüfung der SOUL-Basis (2. Sept.) und Dirigenten-Architektur für Soul 10.0.0

Berichtspfad: /home/user/nextool/ordnung/docs/research/R14-soul-basis-kritik-und-dirigent.md

Ziel: Chriso fragt ausdrücklich, ob das SOUL-Dirigenten-System vom 2. September die richtige und optimale Basis ist, und erwartet, dass wir Dinge ändern und besser machen. Prüfe adversarial, konstruktiv und mit Belegen aus dem Code (lies gezielt: /home/user/soul/{SOUL.md,CLAUDE.md,PROJEKT-START.md,core/*.py,.claude/settings.json,.claude/agents/*.md,gates/README.md,playbooks/*.md,knowledge/*.md}; Kontextpaket §2, §10). Nutze außerdem WebSearch/WebFetch für den Stand der Kunst bei Long-Running-Agent-Harnesses (Anthropic Two-Agent-Harness/„effective harnesses for long-running agents", Claude Code Agent Teams, Workflows, Ralph-Loop-Kritik, OpenHands/Devin-Architekturen, Codex-Cloud-Tasks, Manus, „agent orchestration depth" Studien, Delegations-Verträge, Kosten-/Kontingent-Management).

1. **Kritik der Basis:** Für jedes der sieben Organe: Was trägt (mit Beleg im Code oder in Chrisos Messungen)? Was ist Verwaltung statt Wirkung? Was ist nur spezifiziert, nie gelaufen (Beleg: gates/SOL-LOG.md ist leer; missions/ existiert nicht im Repo; watch/ enthält zwei kurze Event-Logs)? Was fehlt für Chrisos Zielbild (Projekt allein zu Ende führen, 3–6 Ebenen, Ressourcen optimal nutzen, universell für jeden Nutzer/jedes Modell, nicht nur Chrisos Mac)? Was ist Mac-spezifisch (zsh, pbcopy, open, Desktop .command) und muss für Universalität abstrahiert werden? Bewerte die Ausnahmeliste (guard.py) gegen „null Kontrolle": was davon ist Ring 2 im Sinne eines Nutzers, was ist unnötige Bremse?
2. **Dirigenten-Schleife als Kern:** Entwirf die oberste Denkschleife (Chrisos Fragen: Was ist optimal möglich? Was gibt es? Was kann ich nutzen/bauen/vorbereiten/organisieren? Was delegiere ich wie/wann an wen? Wie/wann prüfe ich? Bis fertig.) als präzisen, modellgerichteten englischen Text (300–800 Wörter), der in Ordnungs Kernel bzw. in ein „conductor"-Modul passt — mit Stoppregeln, Ebenen-Entscheidung (wann Subagent, wann Team, wann Workflow, wann eigener Chat/Session, wann Cross-Model-Gegenstimme), Übergabe-Vertrag pro Ebene (Ziel, Nicht-Ziele, Inputs, Abnahmeprobe, Rückkanal), Verifikationspunkten (Beleg ≠ Urteil), Kontingent-Bewusstsein (Wellen-Regel, Limits ehrlich planen) und Fehlweg-Reflex.
3. **Ebenen-Modell 1–6:** Rollen je Ebene, Spawn-Tiefe (Claude Code erlaubt CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH), wie Ebene 4–6 über Workflows/Agent Teams/separate Sessions (Claude Code Remote, `claude -p`, Codex, andere Modelle) erreicht werden, wie Zustand zwischen Ebenen fließt (Dateien, missions/, receipts), Kosten und Ausfallverhalten (der Prüfer fällt zuerst weg).
4. **Universalität:** Was muss geändert werden, damit Soul 10 für jeden Nutzer läuft (Onboarding: einmal gebündelt fragen — Freischaltungen, Logins, Vorinstallationen; Profil-Erkennung: welches Modell, welche Abos, welches Gerät), plattformneutrale Starter (macOS/Linux/Windows), Plugin-Verpackung, keine hartkodierten Pfade.
5. **Verbesserungsliste:** 15–30 konkrete Änderungen am SOUL-Stand (Datei, was, warum, Aufwand, Beleg), sortiert nach Wirkung; klar getrennt in „behalten", „ändern", „streichen", „neu".

Liefere: Kritik je Organ, Dirigenten-Schleife (Text), Ebenen-Modell, Universalitäts-Anforderungen, Verbesserungsliste — alles als Bauvorlage.
