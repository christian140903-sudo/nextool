# R04 — Bindung an andere Modelle und Werkzeuge (Portabilität)

*Recherche-Front R04 für Ordnung × SOUL (Produkt Soul 10.0.0). Stand 2026-09-06. Autor: Recherche-Agent (Fable 5.1). Quellenregel: nur, was in Tool-Ergebnissen gesehen wurde; Erinnerungswissen ist als [unverifiziert] markiert. Claude Code selbst ist Front R03 und wird hier nur als Referenzpunkt erwähnt.*

## 1. Kernaussagen (mit Quellen)

1. **AGENTS.md ist der eine Träger, der fast alles abdeckt.** Offiziell belegt für Codex, Cursor (nested), GitHub Copilot, Kiro, OpenCode, Cline, Windsurf/Devin, Gemini CLI (via `context.fileName`); sekundär für Aider, Zed, Roo, Amazon Q, Jules, Amp. Das Kompilat braucht **ein** AGENTS.md; alle Sonderformate sind Ableitungen. (2.1–2.3)
2. **Agent Skills (agentskills.io) sind der zweite universelle Träger — 46 Clients gelistet — und der einzige mit On-Demand-Laden.** Kernel → AGENTS.md (immer da, klein); Module → Skills (nur bei Signal, `description` = Auslösebedingung). Codex begrenzt die Skill-Liste auf 2 % des Kontexts / 8.000 Zeichen. (2.7, 2.1)
3. **Codex CLI hat dasselbe Hook-Modell wie Claude Code** (SessionStart … PreCompact, SubagentStart/Stop; `hooks.json`; Exit 2 = Block; MCP-Tool-Hooks). SOULs Wache/Briefing/Guard ist 1:1 portierbar. Maximale Autonomie: `approval_policy="never"` + `sandbox_mode="danger-full-access"`. (2.1)
4. **Gemini CLI ist das einzige Agenten-Tool mit `BeforeModel`/`AfterModel`-Hooks** — Frame-Stufe pro Modellaufruf und Antwort-Abgriff ohne Proxy; Import-Syntax `@file`; Skills nativ; YOLO nur per CLI-Flag; Extensions bündeln Kontext + Hooks + MCP + Skills wie ein Claude-Plugin. (2.2)
5. **Harte Budgets sind belegt:** Codex 32 KiB AGENTS-Gesamtbudget (stiller Abschnitt!), Windsurf 6.000/12.000 Zeichen, Cursor < 500 Zeilen, ChatGPT/GPTs/Claude Projects ≈ 8.000 Zeichen, Ollama `num_ctx` Default 2048, Anthropic Cache-Minimum 512–4.096 Tokens je Modell. Daraus folgt S ≈ 600 / M ≈ 2.000 / L ≈ 6.000 Tokens. (2.9)
6. **Der OpenAI Model Spec (2026-08-18) verlangt „bounded autonomy" über einen vereinbarten „scope of autonomy"** (Teilziele, Nebenwirkungen, Eskalationspunkte) und „pause for approval" bei irreversiblen Aktionen. Ordnungs Autonomie-Charta muss für OpenAI-Modelle in diesem Vokabular formuliert sein — „null Bremsen" wird sonst vom Root-Level ignoriert; Ring 2 = Eskalationspunkte. (2.1)
7. **Responses-API-`instructions` gelten nur für die aktuelle Anfrage** (nicht mit `previous_response_id` persistiert) → Kernel bei jedem Aufruf mitsenden; Proxy tut das. (2.1)
8. **Prompt-Caching macht Kernel-Größe fast kostenlos, aber nicht wirksam:** Read 0,1× (Fable 5.1/Mythos 5.1: 0,025×), 4 Breakpoints, Hierarchie tools→system→messages. Argument gegen große Kernel ist Adhärenz, nicht Preis; Kernel S wird auf Haiku 4.5 (Min 4.096) gar nicht gecacht. (2.4)
9. **MCP kann Gedächtnis, Selbstmodell und Prüf-Prompts tragen, aber keinen Kernel garantieren** (kein System-Prompt-Kanal außer dem ungeprüften Server-`instructions`-Feld). Brücke: Hooks fragen den MCP-Server bei SessionStart. soul-mcp 4.0.2 (2026-08-14, 23 Tools) ist Erz: richtige Absicht (Provenance, Receipts), aber ohne Selbstkenntnis; neu bauen mit ≤ 8 Tools + Resources + Prompts. (2.6)
10. **Der Proxy ist Träger Nr. 3** — für lokale/OpenAI-kompatible Modelle, die Evaluationsstrecke und Clients ohne Dateien; Nachteile: sieht keine Tool-Ereignisse, und ein vorangestellter Frame bricht den Client-Cache-Präfix. `implant-v10` bleibt byte-gleich als Vergleichsarm. (2.8)
11. **Lokale Modelle: Evidenz ist dünn und architekturabhängig** (Qwen3-4B stabil, Gemma-3-4B/Granite-3.1-3B kollabieren unter Multi-Task-Prompts; 7–8B-Modelle folgen System-Prompts schwächer); eigene Messungen zeigen Richtungsumkehr und Formatschaden. Regel: nur S, formatneutral, Selbsttest vor Aktivierung, Ergebnis ins Kalibrierungsgedächtnis. (2.5)
12. **`~/.agents/` ist der entstehende tool-übergreifende Home-Ort** (Codex `~/.agents/skills`, Cline `~/.agents/AGENTS.md`); OpenCode und Copilot-Agent lesen CLAUDE.md direkt → der Kernel-Text muss tool-neutral sein, Tool-Interna gehören in Tool-Config. (2.3)


## 2. Detailbefunde

### 2.1 OpenAI: Codex CLI, ChatGPT Projects/Custom GPTs, OpenAI API

**Befund vorab: Die Codex-Dokumentation ist umgezogen.** `developers.openai.com/codex/...` antwortet mit 308 auf `learn.chatgpt.com/docs/...` (gesehen 2026-09-06). Wer Installationsanleitungen mit Links schreibt, muss die neuen URLs verwenden; alte Links in ANIMA v3 `model-adapters.md` sind damit tot.

**Codex CLI — Instruktionsdatei (AGENTS.md).** Offizielle Regeln (learn.chatgpt.com/docs/agent-configuration/agents-md):
- Reihenfolge: global `~/.codex/AGENTS.override.md` (falls vorhanden), sonst `~/.codex/AGENTS.md`; dann Projekt-Scope: vom Git-Root abwärts bis zum aktuellen Verzeichnis, pro Ebene `AGENTS.override.md` → `AGENTS.md` → Fallback-Namen; „includes at most one file per directory".
- Zusammenführung: „Codex concatenates files from the root down, joining them with blank lines. Files closer to your current directory override earlier guidance because they appear later in the combined prompt." — Also KEIN Import-Mechanismus wie Claude Codes `@pfad`, sondern reine Konkatenation. Ein Ordnung-Kernel kann daher nicht per Verweis eingebunden werden; er muss physisch in AGENTS.md stehen oder per Skill nachgeladen werden.
- **Größenlimit: 32 KiB Gesamtbudget** (`project_doc_max_bytes`, Default 32 KiB): „Codex skips empty files and stops adding files once the combined size reaches the limit" — d. h. bei Überschreitung werden spätere (projektnähere) Dateien **stillschweigend abgeschnitten**, nicht die globale. Für Soul 10 heißt das: Der global installierte Kern (`~/.codex/AGENTS.md`) frisst vom selben 32-KiB-Budget wie die Projektdateien des Nutzers. Ein 20-KB-Kernel würde Projekt-AGENTS.md von Nutzern beschneiden — unsichtbar. Budgetempfehlung: globaler Ordnung-Kern für Codex ≤ 8 KiB (siehe 2.9).
- `project_doc_fallback_filenames` in `~/.codex/config.toml` erlaubt zusätzliche Dateinamen (z. B. `TEAM_GUIDE.md`, `.agents.md`) — damit könnte man `ORDNUNG.md` als Fallback registrieren, aber nur, wenn KEIN AGENTS.md im selben Verzeichnis liegt (eine Datei pro Ebene).

**Codex CLI — config.toml** (learn.chatgpt.com/docs/config-file/config-reference):
- `approval_policy`: `"untrusted"`, `"on-request"`, `"never"`; `"on-failure"` ist deprecated. Granular: `approval_policy = { granular = { sandbox_approval, rules, mcp_elicitations, request_permissions, skill_approval } }`.
- `sandbox_mode`: `"read-only"`, `"workspace-write"`, `"danger-full-access"`. **Maximale Autonomie = `approval_policy = "never"` + `sandbox_mode = "danger-full-access"`** — das Codex-Äquivalent zu SOULs `bypassPermissions`.
- `model_reasoning_effort`: `"minimal"|"low"|"medium"|"high"|"xhigh"` (modellabhängig); `model_reasoning_summary`: `auto|concise|detailed|none`. Das ist der Hebel für Tiefensteuerung von außen — ein Router könnte pro Profil den Effort setzen.
- `model_instructions_file`: „path to custom instructions replacing built-ins" — **ersetzt die eingebaute Systemanweisung von Codex komplett.** Mächtigster, aber riskantester Einstiegspunkt (man verliert OpenAIs Tool-Anleitungen). Für Soul 10 nur als Experimentier-Arm, nicht Default.
- `model_context_window`, `model` (Beispiel in der Doku: `"gpt-5.5"`).
- `[mcp_servers.<id>]` mit `command`, `args`, `cwd`, `env`, `url` (HTTP), `enabled`, `required`, per-Tool-Approval.
- `[features]`: z. B. `unified_exec = true`, `memories = true` — **Codex hat einen nativen Memories-Feature-Flag** (Details 2.1.1).
- Profile: `--profile name` → `$CODEX_HOME/name.config.toml`. Damit lassen sich „Miguel für alle" / „vollständiger Miguel" als zwei Codex-Profile abbilden, ohne Dateien zu tauschen.

**Codex CLI — Hooks** (learn.chatgpt.com/docs/hooks): „Codex CLI fully supports lifecycle hooks", standardmäßig aktiv (`[features] hooks = false` schaltet ab). Events: `SessionStart`, `SessionEnd`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `Interrupt`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`. Konfiguration in `hooks.json` oder `[hooks]`-Tabellen in `config.toml`, Orte: `~/.codex/hooks.json`, `~/.codex/config.toml`, `<repo>/.codex/hooks.json`, `<repo>/.codex/config.toml`. Zwei Handler-Typen: Command-Hooks (Shell/Python) und **MCP-Tool-Hooks** (rufen Tools verbundener MCP-Server). Semantik: Exit 0 + JSON = Entscheidung (`continue`, `stopReason`, `systemMessage`); Exit 2 = blockierend mit stderr als Grund; Klartext-stdout wird als Developer-Kontext hinzugefügt (eventabhängig). Timeout 600 s (SessionEnd 1 s).
→ **Das ist praktisch dasselbe Ereignismodell wie Claude Code.** SOULs `hook.py` → `core/events.py` (JSONL-Wache, Guard-Ausnahmeliste, SessionStart-Briefing, PreCompact) ist damit **1:1 auf Codex portierbar**, inklusive Gedächtnis-Injektion via SessionStart-stdout. Die Existenz von MCP-Tool-Hooks bedeutet: Ein Ordnung-MCP-Server kann seine Hook-Logik selbst anbieten (ein Server, zwei Clients).

**Codex CLI — Skills** (learn.chatgpt.com/docs/build-skills): `SKILL.md` mit Pflicht-Frontmatter `name`, `description`; optionale `scripts/`, `references/`, `assets/`, `agents/openai.yaml`. Suchorte: `$CWD/.agents/skills`, `$REPO_ROOT/.agents/skills`, `$HOME/.agents/skills`, `/etc/codex/skills`, plus eingebaute. Aufruf explizit (`$skill` in Codex CLI, `@skill` in ChatGPT) oder implizit über die description (abschaltbar mit `allow_implicit_invocation`). **Kontextbudget: die Skill-Liste kostet „at most 2% of the model's context window, or 8,000 characters when the context window is unknown"; erst bei Auswahl wird das ganze SKILL.md geladen.** Die Doku nennt ausdrücklich den „open agent skills standard" (agentskills.io). Konsequenz: Ordnungs Module (Faktor-Spezialisten) können als Skills unter `~/.agents/skills/` liegen und werden **von Codex UND Claude Code** (Front R03) gefunden — ein Verzeichnis, zwei Werkzeuge; die 2-%-Regel begrenzt, wie viele Module es sein dürfen (Beschreibungen kurz halten, ca. 10–20 Skills realistisch).

**OpenAI Responses API** (developers.openai.com/api/docs/guides/text): `instructions`-Parameter ≙ `developer`-Rolle („Talk like a pirate" als Beispiel für beide Wege); die Doku nennt nur `developer`, `user`, `assistant` — kein `system`. Priorität: „developer messages are instructions provided by the application developer, prioritized ahead of user messages." **Wichtig für Gedächtnis/Kernel-Persistenz: „the instructions parameter only applies to the current response generation request. If you are managing conversation state with the previous_response_id parameter, the instructions used on previous turns will not be present in the context."** → Ein Ordnung-Kernel muss bei jeder Anfrage erneut mitgesendet werden (was auch Prompt-Caching begünstigt: stabiler Präfix). Der Proxy-Ansatz (2.8) tut genau das.

**OpenAI Model Spec (Version 2026-08-18, model-spec.openai.com/2026-08-18.html):** Fünf Autoritätsstufen: Root („cannot be overridden by system messages, developers or users") > System (OpenAI-Regeln) > Developer > User > Guideline („can be implicitly overridden"). Developer dürfen User- und Guideline-Defaults überschreiben; nicht: Root/System, das Spec verstecken/ignorieren. Zitat: „we aim to give developers broad latitude, trusting that those who impose overly restrictive rules on end users will be less competitive in an open market." **Agentik: Das Spec verlangt „bounded autonomy" über eine explizite „scope of autonomy"-Vereinbarung (erlaubte Teilziele, akzeptable Nebenwirkungen — Zeit, Geld, Datenzugriff — und Eskalationspunkte), und: „The assistant must adhere strictly to the agreed scope (subject to the chain of command) unless explicitly updated and approved by the original user or developer."** Für hochriskante, irreversible Aktionen „must pause for clarification or approval".
→ Das trifft Soul 10s „consent by design" (Kontextpaket §11b) frontal und **bestätigt es zugleich**: OpenAIs Modelle sind darauf trainiert, einen vorab vereinbarten Autonomieumfang zu respektieren — genau das ist die Onboarding-Zustimmung. Aber: Der Scope muss dem Modell *im Prompt* als vereinbart mitgeteilt werden (Developer-Ebene), sonst fällt GPT auf „pause for approval" zurück. Die Ring-2-Liste ist im Model-Spec-Vokabular exakt die „escalation points". Ordnungs Autonomie-Charta muss für OpenAI-Ziele als *scope-of-autonomy*-Block formuliert werden (Teilziele, Nebenwirkungen, Eskalationspunkte), nicht als „null Bremsen"-Deklaration — letztere würde vom Root-Level ignoriert.

**ChatGPT Projects / Custom GPTs** (help.openai.com lieferte 403; Zahlen aus Sekundärquellen via WebSearch, daher „Sekundär"): Projekt-Instruktionen bis **8.000 Zeichen**; Dateien je Projekt **5 (Free) / 25 (Go, Plus) / 40 (Pro, Business, Edu, Enterprise)**; Projekt-Instruktionen gelten unabhängig von globalen Custom Instructions; Projekt-Memory („project-only memory") existiert als Komponente. Custom GPTs: **8.000 Zeichen Instruktionen, 20 Knowledge-Files, 512 MB/Datei, 2 M Tokens/Textdatei** (OpenAI Developer Community, mehrere Threads). → Für ChatGPT ist der Kernel auf ~8.000 Zeichen (≈ 2.000 Tokens) begrenzt = Größe **S** des Kompilats (2.9); Module und Gedächtnis-Exporte müssen als Knowledge-Files beigelegt werden, die das Modell per Retrieval liest (nicht deterministisch geladen). Skills in ChatGPT: `@skill`-Aufruf ist dokumentiert (build-skills-Seite), was ChatGPT zum zweiten Träger für Ordnungs-Skills macht.

### 2.2 Google: Gemini CLI, Gemini API, Gems

**Gemini CLI — Kontextdatei GEMINI.md** (geminicli.com/docs/cli/gemini-md/): Drei Ebenen — global `~/.gemini/GEMINI.md`; Workspace-Dateien in Arbeitsverzeichnissen **und deren Elternverzeichnissen**; „Just-in-time context": wenn Tools Dateien anfassen, scannt die CLI das betreffende Verzeichnis und Vorfahren bis zu einer vertrauenswürdigen Wurzel. Dateiname konfigurierbar: `settings.json` → `"context": {"fileName": ["AGENTS.md", "CONTEXT.md", "GEMINI.md"]}` — **Gemini CLI kann also direkt AGENTS.md lesen**, was für das Kompilat bedeutet: ein AGENTS.md deckt Codex + Gemini CLI + OpenCode (2.3) ab, GEMINI.md ist optional. **Import-Syntax existiert: `@./components/instructions.md`, `@../shared/style-guide.md`** (relativ und absolut) — Gemini CLI verhält sich hier wie Claude Code (`@`-Import) und anders als Codex (reine Konkatenation). Alles Gefundene wird konkateniert und „sent to the model with every prompt". Befehle: `/memory show`, `/memory reload`. Größenlimit: **nicht dokumentiert**; Discovery-Grenze `context.discoveryMaxDirs` = 200, `context.loadMemoryFromIncludeDirectories` = false (settings-Referenz).

**Gemini CLI — Hooks** (geminicli.com/docs/hooks/): Elf Events: `SessionStart`, `SessionEnd`, `BeforeAgent` (nach Prompt, vor Planung), `AfterAgent`, **`BeforeModel` („Before sending request to LLM"), `AfterModel`**, `BeforeToolSelection`, `BeforeTool`, `AfterTool`, `PreCompress`, `Notification`. Konfiguration in `hooks`-Sektion der `settings.json` (Projekt `.gemini/settings.json` → User `~/.gemini/settings.json` → System `/etc/gemini-cli/settings.json` → Extensions). Exit 0: stdout als JSON geparst; Exit 2: „Critical Block. The target action (tool, turn, or stop) is aborted"; **„Your script must not print any plain text to stdout other than the final JSON object"** (anders als Codex, wo Klartext-stdout als Kontext gilt — ein Portierungsfallstrick). Timeout 60 s. Env: `GEMINI_PROJECT_DIR`, `GEMINI_SESSION_ID`, `GEMINI_CWD`. `hooksConfig.enabled` Default true.
→ **`BeforeModel`/`AfterModel` sind einzigartig unter den CLI-Agenten:** Hier kann Ordnung den gemessenen Frame oder eine situationsabhängige Frame-Stufe (N5, voll/reduziert/keine) **pro Modellaufruf** einsetzen und die Antwort **nach jedem Aufruf** für Kalibrierung/Entropie-Messung abgreifen — exakt die Proxy-Funktion (2.8), aber ohne Proxy. Für Claude Code und Codex gibt es das nicht (dort nur UserPromptSubmit/PreToolUse). Für die Evaluation ist Gemini CLI damit die beste Host-Umgebung für Selbstkonsistenz@3- und Placebo-Arme im echten Agentenbetrieb.

**Gemini CLI — Approval/Autonomie** (settings-Referenz): `general.defaultApprovalMode`: `"default"` (fragt), `"auto_edit"` (Edits automatisch), `"plan"` (read-only). **„YOLO mode (auto-approve all actions) can only be enabled via command line (--yolo or --approval-mode=yolo)"** — die maximale Autonomie ist bewusst nicht persistent konfigurierbar; ein Soul-10-Starter (wie `bin/soul start`) muss die CLI-Flagge setzen. `skills.enabled` Default true → **Gemini CLI unterstützt Agent Skills nativ.**

**Gemini CLI — Extensions** (geminicli.com/docs/extensions/): `gemini extensions install <git-url>`; eine Extension bündelt „prompts, MCP servers, custom commands, themes, hooks, sub-agents, and agent skills". → **Eine Gemini-Extension ist das Gegenstück zum Claude-Code-Plugin** (Kernel-Kontextdatei + Hooks + MCP + Skills + Sub-Agenten in einem Git-Repo). Soul 10 sollte aus derselben Quellstruktur ein `gemini-extension.json` erzeugen; Feldschema in der Referenzseite (nicht abgerufen, [unverifiziert]: Felder `name`, `version`, `mcpServers`, `contextFileName`).

**Gemini API** (ai.google.dev/gemini-api/docs/text-generation): Systemanweisung über `system_instruction`; Tiefe über `generation_config.thinking_level` (Beispiel `"low"`; „each model supports different thinking configurations"). Längenlimit für `system_instruction` nicht dokumentiert. → Für API-Bindung: Kernel als `system_instruction`, Router setzt `thinking_level` (Pendant zu Codex `model_reasoning_effort` und Anthropic-Effort).

**Gems** (support.google.com/gemini/answer/15235603): Instruktionen nach Schema Persona/Task/Context/Format; Datei-Uploads möglich; **keine Zeichen- oder Dateilimits auf der Seite angegeben**; Gedächtnis nur innerhalb einer Konversation beschrieben. → Gems = Kompilat-Größe S/M (Textfeld) + Dateien als Wissen; kein Hook, kein persistentes Gedächtnis, kein MCP: niedrigste Bindungsstufe („Text-only-Ziel").

### 2.3 IDE-Agenten: Cursor, Windsurf, Cline, Roo Code, Aider, GitHub Copilot, Zed, JetBrains, Kiro, Amazon Q, OpenCode, Goose

**Der eine Befund, der alles andere ordnet: AGENTS.md ist 2026 der De-facto-Standard.** Offiziell dokumentiert gesehen für: Codex (2.1), Gemini CLI (über `context.fileName`, 2.2), **Cursor** („Nested AGENTS.md support in subdirectories is now available" — cursor.com/docs/context/rules), **GitHub Copilot** (`AGENTS.md`, „nearest in directory tree takes precedence", oder ein einzelnes `CLAUDE.md`/`GEMINI.md` im Root — docs.github.com), **Kiro** („supports the AGENTS.md standard — discovered in workspace root and subdirectories, always included without mode configuration" — kiro.dev/docs/steering), **OpenCode** (Primärformat; `CLAUDE.md` als Fallback — opencode.ai/docs/rules), **Cline** (`AGENTS.md` oder `~/.agents/AGENTS.md`, „Cross-tool compatible" — docs.cline.bot). Sekundärquellen (WebSearch, mehrere 2026-Guides) nennen zusätzlich Aider, Zed, Roo Code, Amazon Q, Windsurf, Devin, Jules, Amp, Continue, Factory. **Folge: Das Kompilat braucht genau EIN AGENTS.md als Hauptartefakt; alles andere sind Sonderfälle.**

**Zweiter Befund: Mehrere Tools lesen CLAUDE.md direkt.** OpenCode: Projekt `AGENTS.md` → Fallback `CLAUDE.md`; global `~/.config/opencode/AGENTS.md` → Fallback `~/.claude/CLAUDE.md`; abschaltbar per `OPENCODE_DISABLE_CLAUDE_CODE=1`, `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1`, **`OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1`** (d. h. OpenCode lädt auch Claude-Code-Skills!). Copilot coding agent: `CLAUDE.md`/`GEMINI.md` im Root. → Wer Ordnung für Claude Code (R03) installiert, hat es damit in OpenCode und dem Copilot-Agenten **bereits installiert** — Vorsicht: dann gelten Claude-spezifische Formulierungen (Hook-Namen, `@`-Importe) in einem Tool, das sie nicht versteht. Der CLAUDE.md-Import von Ordnung muss daher tool-neutral formuliert sein (keine Claude-Code-Interna im Kernel-Text; Interna in `.claude/`-Konfiguration).

**Cursor** (cursor.com/docs/context/rules): `.cursor/rules/*.mdc`, versioniert; Frontmatter `description`, `globs`, `alwaysApply`; vier Typen: Always Apply / Apply Intelligently (Agent entscheidet per description) / Apply to Specific Files (globs) / Apply Manually (`@`-Mention). **„Keep rules under 500 lines", „Split large rules into multiple, composable rules."** Reihenfolge Team Rules → Project Rules → User Rules; User Rules gelten nur im Agent-Chat, nicht in Inline Edit. AGENTS.md nested unterstützt („plain markdown alternative … without requiring frontmatter"). Memories/legacy `.cursorrules`/CLAUDE.md nicht auf der Seite. → Cursor-Set: `000-ordnung-kernel.mdc` (alwaysApply: true, < 500 Zeilen) + Module als „Apply Intelligently"-Regeln mit präziser description = Cursor-Äquivalent zu Skills (Auto-Aktivierung nach Beschreibung). Keine Hooks, kein Gedächtnis-API → Gedächtnis nur via MCP (2.6).

**GitHub Copilot** (docs.github.com): `.github/copilot-instructions.md` (repo-weit), `.github/instructions/NAME.instructions.md` mit `applyTo`-Globs (+ optional `excludeAgent: code-review|cloud-agent`), `AGENTS.md`. „Path-specific custom instructions are only supported for Copilot cloud agent and Copilot code review" auf GitHub.com. Priorität: „Personal instructions take the highest priority. Repository instructions come next, and then organization instructions". Längenrichtwert nur indirekt: „Instructions must be no longer than 2 pages" (Vorgabe an den Generator). Keine harten Limits dokumentiert. → Copilot ist ein Text-only-Ziel ohne Hooks/Memory; sinnvoll für den **Coding-Agent-Betrieb** (asynchrone PR-Agenten), wo Ordnungs Kernel S/M als `copilot-instructions.md` liegt.

**Windsurf** (docs.windsurf.com → 307-Redirect auf docs.devin.ai/desktop/cascade/memories; Details siehe Nachtrag unten, falls abgerufen): Windsurf-Doku lebt jetzt unter Devin (Cognition). Rules mit Aktivierungsmodi und Zeichenlimits — Zahlen nur, wenn im Nachtrag belegt.

**Kiro** (kiro.dev/docs/steering): `.kiro/steering/*.md` (Workspace) + `~/.kiro/steering/` (global; Workspace gewinnt bei Konflikt); Grunddateien `product.md`, `tech.md`, `structure.md`; Frontmatter `inclusion: always | fileMatch (fileMatchPattern) | manual (#steering-file-name) | auto (name, description)`; Live-Dateiverweise `#[[file:api/openapi.yaml]]`; „CLI doesn't support inclusion modes; all .kiro/steering/ files load automatically". → Kiro ist strukturell das reichste IDE-Format (vier Lademodi = exakt Ordnungs Tiefenstufen: immer/nach Signal/manuell/nach Dateityp) und **erlaubt Live-Verweise** auf das Gedächtnis (`#[[file:~/.ordnung/briefing.md]]`), ohne Hook.

**Anthropic Messages API — System-Prompt und Caching** (platform.claude.com/docs/en/build-with-claude/prompt-caching, verbindliche Zahlen):
- Mindestlänge für Caching: **512 Tokens** (Fable 5.1, Mythos 5.1, Opus 5, Fable 5, Mythos 5), **1.024** (Opus 4.8, Sonnet 5, Sonnet 4.6/4.5, Opus 4.1/4), **2.048** (Mythos Preview, Opus 4.7, Haiku 3.5), **4.096** (Opus 4.6/4.5, Haiku 4.5). „Shorter prompts cannot be cached, even if marked with cache_control … no error is returned."
- TTL 5 min (Default) oder 1 h (`"ttl": "1h"`); Preise: 5-min-Write 1,25×, 1-h-Write 2×, **Read 0,1× — bei Fable 5.1 und Mythos 5.1 nur 0,025×**. Beispiel Opus 5: Base 5 $/MTok, Hit 0,50 $/MTok.
- Bis zu **4 Breakpoints**; Präfix-Hierarchie **tools → system → messages** („Changes at each level invalidate that level and all subsequent levels"); Lookback 20 Blöcke; Breakpoint „on the last block whose prefix is identical across requests", nie auf den variablen Block.
→ **Drei harte Konsequenzen für das Kompilat:** (1) Ein Kernel unter 512–4.096 Tokens (je Modell) wird bei kleinen Modellen (Haiku 4.5: 4.096!) **gar nicht gecacht** — Größe S (≈ 600 Tokens) ist auf Haiku 4.5 jedes Mal Vollpreis; erst Größe M/L profitiert. (2) Bei 0,1× (bzw. 0,025×) Read kostet ein 3.000-Token-Kernel effektiv 300 (75) Token-Äquivalente pro Aufruf — **die Kosten sind NICHT das Argument gegen einen größeren Kernel; das Argument ist Adhärenz/Aufmerksamkeit** (Front R02) und der Deckeneffekt. (3) Schichtung im System-Array: Block 1 Kernel (statisch, Breakpoint 1) → Block 2 Modulauswahl/Profil (ändert sich je Projekt, Breakpoint 2) → Block 3 Gedächtnis-Briefing (ändert sich je Sitzung, Breakpoint 3) → Messages. SOULs `ENABLE_PROMPT_CACHING_1H=1` und `subagentPromptCacheTtl: 1h` passen zur 1-h-TTL, kosten aber 2× beim Schreiben — lohnt nur, wenn Sitzungen > 5 min pausieren (Dirigent mit Unteragenten: ja).

**Claude Agent SDK:** nicht abgerufen (Kontingent). [unverifiziert]: Python/TypeScript-SDK mit `system_prompt`, Laden von CLAUDE.md über `setting_sources`, Hooks und MCP-Server programmatisch — d. h. eine SDK-eingebettete Ordnung nutzt das Claude-Code-Plugin-Format (R03) wieder. ### 2.5 Lokale/offene Modelle: Ollama, LM Studio, llama.cpp, vLLM, Open-WebUI — und die Robustheit kleiner Modelle

**Ollama — Modelfile** (docs.ollama.com/modelfile): Instruktionen `FROM <model>:<tag>` (Pflicht), `SYSTEM """…"""` (mehrzeilig mit Triple-Quotes), `TEMPLATE """{{ if .System }}…{{ end }}…"""` (Go-Template mit `{{ .System }}`, `{{ .Prompt }}`, `{{ .Response }}`), **`PARAMETER num_ctx <int>` — „Sets the size of the context window used to generate the next token. (Default: 2048)"**, `MESSAGE <system|user|assistant> <text>` (vorgefertigte Konversationshistorie), `ADAPTER <path>` (LoRA, Safetensor/GGUF), `LICENSE`. Bauen: `ollama create <name> -f ./Modelfile`. Reihenfolge der Instruktionen egal, case-insensitive. **Nicht dokumentiert: wie ein per API mitgeschicktes `system` mit dem Modelfile-SYSTEM zusammenwirkt** ([unverifiziert]: nach Erinnerung ersetzt die Request-System-Message das Modelfile-SYSTEM; muss vor dem Bau des Ollama-Adapters mit einem 2-Zeilen-Test geprüft werden).
→ **Drei Design-Folgen:** (1) Ein Ordnung-Modelfile MUSS `PARAMETER num_ctx` explizit setzen (mind. 8192, besser 16384–32768 je nach RAM), sonst schneidet der Default 2048 einen Kernel + Aufgabe ab — das ist exakt die Formatschaden-Klasse aus Kontextpaket §3 (Plan ohne Code). (2) `MESSAGE`-Zeilen erlauben Few-Shot-Einpflanzung des Verhaltens (ein Beispiel „stiller Frame → knappe Lieferung") — für 7B–14B-Modelle vermutlich wirksamer als Prosa-Regeln (Hypothese, zu messen). (3) `ADAPTER` ist der einzige Weg unter allen Zielen, Ordnung tatsächlich **in Gewichte** zu bringen (LoRA aus eigenen Logs) — bewusst NICHT Teil von Soul 10 (Kontextpaket §6: „Dateien ändern keine Gewichte; wir bauen keine Umgehung"), aber als späterer Forschungsarm notierbar.

**LM Studio, llama.cpp, vLLM, Open-WebUI** — nicht per Fetch belegt (Kontingent), daher [unverifiziert] aus Erinnerung: alle vier bieten einen **OpenAI-kompatiblen HTTP-Endpunkt** (LM Studio `localhost:1234/v1`, `llama-server` mit `--system-prompt-file`, vLLM `vllm serve` mit Chat-Template des Modells, Open-WebUI mit System-Prompt je „Model"-Profil und je Nutzer). Der belastbare Schluss hängt daran nicht: **Da alle lokalen Server OpenAI-kompatibel sprechen, ist der Proxy (2.8) der EINE Träger, der jedes lokale Modell ohne Server-spezifische Konfiguration abdeckt** — Ordnung als System-Message-Injektion vor dem Upstream. Ollama-Modelfile bleibt die Alternative für Nutzer ohne Proxy („`ollama run ordnung-qwen`").

**Robustheit kleiner Modelle gegenüber langen Struktur-Prompts — Evidenzlage:**
- Eigene Messungen (Kontextpaket §3, verbindlich): Richtungsumkehr zwischen Modellen (Antwortlänge B/A 0,65 bei gpt-oss-120b vs. 1,41 bei qwen); Formatschaden durch Ausgabe-Anweisungen (2/30 Antworten zerstört); Deckeneffekt bei 93–97 % nackt; „unbekannte Modelle als strong behandeln" (modelTier.ts, Rückfall auf `strong` = „Ausgabeformat nicht anfassen").
- Externe Befunde (WebSearch, Sekundärzusammenfassung; Primärquellen nicht vollständig gelesen): Llama-3.1-8B-Instruct und Qwen-2.5-7B-Instruct zeigen „weaker adherence to system prompts compared to larger models" (Scale-AI-Beitrag zu Long-Context-Instruction-Following); Multi-Task-Prompting-Degradation ist **stark architekturabhängig** — „Qwen3 4B maintained stable performance, Gemma 3 4B and Granite 3.1 3B exhibited severe collapses" (MDPI Electronics 14(21):4349, 2025); Long-CoT-SFT verschlechtert kleine Modelle („Through the Valley", arXiv 2506.07712). Keine gefundene Studie misst gezielt „System-Prompt-Länge × Modellgröße" auf IFEval — **Lücke**, die Soul 10 selbst schließen muss (N4 gemessene Modell-Passung).
- ANIMA v3 `model-adapters.md` (lokal, §6) beschreibt für Llama < 70B „coherence loss at depth", „instruction drift … reverting to default helpful-assistant behavior", „repetition under pressure" und empfiehlt „shorter, more focused modules with frequent checkpoints" und „periodic reinforcement prompts" — plausibel, aber **unbelegt** (keine Messung im Dokument), und die Diagnostik-Prompts dort messen Selbstbericht, nicht Leistung.
→ **Regel für lokale Ziele:** nur Kompilat-Größe **S** (≤ 600 Tokens, siehe 2.9), keinerlei Ausgabeformat-Anweisung, keine Meta-Zeilen (Annahme/Abweichung entfallen, wie in der formatneutralen Frame-Variante), und **vor der Aktivierung ein automatischer 3×10-Aufgaben-Selbsttest gegen nackt** (Eigenstreuung erst messen — §3: unveränderter Arm schwankte 6,7–13,3 pp). Fällt der Frame durch, läuft das lokale Modell nackt und der Router weiß es (Eintrag im Kalibrierungsgedächtnis, nicht Namensraten). Das ist die Umsetzung von „Meisterschaft unter Knappheit" (§11c): Ordnung darf ein schwaches Modell nicht schwächer machen.

### 2.6 MCP als universeller Träger

**Stand des Protokolls** (modelcontextprotocol.io, abgerufen): Dokumentationspfade tragen die Spezifikationsrevision **`2026-07-28`**; MCP verbindet „AI applications like Claude or ChatGPT" mit „data sources …, tools …, and workflows (e.g. specialized prompts)"; als Clients genannt: Claude, ChatGPT, VS Code, Cursor, MCPJam; zusätzlich existiert „Build MCP Apps — interactive apps that run inside AI clients". Die drei Primitiven Tools / Resources / Prompts sind damit bestätigt; die Client-Feature-Matrix (`mcp-availability.com`, per Suche gefunden) war **nicht erreichbar (DNS)**, die offizielle `/clients`-Seite lieferte nur die Übersicht.

**Was offiziell je Client belegt ist:**
- Gemini CLI: MCP-Prompts erscheinen als **Slash-Commands**, Resources werden „automatically" entdeckt (geminicli.com/docs/tools/mcp-server, Suchzusammenfassung).
- Codex CLI: `[mcp_servers.<id>]` (stdio + HTTP), per-Tool-Approval, **`mcp_elicitations`** im granularen Approval (→ Elicitation unterstützt), **MCP-Tool-Hooks** (2.1). Prompts/Resources: [unverifiziert].
- Claude Desktop: nur MCP als Erweiterungsweg (2.4); Tools/Prompts/Resources [unverifiziert vollständig, nach Erinnerung alle drei].
- Cursor, VS Code, ChatGPT: MCP-Unterstützung auf modelcontextprotocol.io genannt; Prompts/Resources-Umfang [unverifiziert] (Erinnerung: Cursor Tools+Prompts+Resources; ChatGPT primär Tools/Connectors).
- Claude Code: R03 (Erinnerung: Prompts als `/mcp__server__prompt`, Resources per `@server:uri`).

**Die entscheidende Grenze:** MCP hat **keinen Kanal, der die Anwesenheit eines Kernels garantiert.** Tools werden nur aufgerufen, wenn das Modell will; Resources nur, wenn Client/Nutzer sie anhängen; Prompts nur, wenn der Nutzer sie auslöst. Der einzige Weg Richtung System-Prompt ist das `instructions`-Feld der Server-Initialisierung ([unverifiziert], in der Spezifikation vorgesehen; ob und wie Clients es in den System-Prompt übernehmen, ist je Client zu messen — Hypothese H-MCP-1). **Folge: MCP ist der Träger für Gedächtnis, Selbstmodell, Kalibrierung und Prüf-Prompts — nicht für den Kernel.** Die Brücke schlagen Hooks: Codex' MCP-Tool-Hooks und Gemini-Hooks können bei `SessionStart` den Ordnung-Server nach dem Briefing fragen und es als Kontext einspeisen; damit wird aus „Server, den man aufrufen kann" ein „Server, der gelesen wird" (Kontextpaket §3: ein Gedächtnis lebt nur, wenn der Arbeitsfluss es liest).

### 2.7 Agent-Skills-Standard (agentskills.io)

### 2.8 Proxy als Träger (Soul-Proxy 4.5)

**Was vorliegt** (lokal gelesen, `/home/user/soul-proxy-45/`): `package.json` „soul-proxy" 0.1.0 — „Soul 4.1.0 Cloud-Proxy (Intent Analysis + Task Restructuring). Eigenständiges Package, kein Code-Import aus soul-mcp 4.0.1." `src/amplify/dispatch.ts`: `AmplifyMode = "implant" | "implant-v10" | "fusion" | "analyzer" | "off"`; `implant-v10` = „die treue Portierung der in study-v10 GEMESSENEN Form"; `fusion` = „6-Punkte-Gerüst plus … UNGEMESSEN bis P1b"; Analyzer „mit 14,7 % klar verloren, dort wird nicht mehr investiert"; Option `density` (Dichte-Satz aus density.ts). `messages.ts`: der Frame wird als **System-Message vorangestellt** („system-Message vorangestellt wird (s. implantAmplify.ts)"), `findLastUserMessage` liefert den Aufgabentext für Signale/Trivialfilter. `formatGuard.ts`: `FormatGuardSignal = "response_format" | "tools" | "tool_choice" | "benchmark_mode"`; leeres `tools`-Array = kein Zwang; `detectFormatConstraint()` schaltet auf die formatneutrale Variante. `modelTier.ts`: `strong | small`, small-Muster VOR strong geprüft, **Unbekanntes → `strong` („unbekanntes Modell — Rückfall auf strong (Ausgabeformat nicht anfassen)")**; die frühere Einstufung war invertiert (claude-fable-5 → small, gpt-5-mini → strong) — dokumentierter Fehler, aus dem die Regel „Namensraten ist unzuverlässig" (N4) stammt.

**Wie Ordnungs Kernel dort läuft:** als neuer `AmplifyMode = "ordnung"` mit versionierten Frame-Varianten (`ordnung-S|M|L`), **neben** `implant-v10`, das byte-gleich als Vergleichsarm bleibt (Kontextpaket §13 Ausnahme a). Der Router (signals.ts + Verhaltensentropie, falls der Proxy Mehrfachaufrufe fährt) wählt die Frame-Stufe (N5: voll/reduziert/keine) und loggt sie; formatGuard bleibt vorgeschaltet; modelTier wird durch das **Kalibrierungsgedächtnis** ersetzt (gemessene Passung je Modell-ID statt Namensmuster — dazu muss der Proxy Ergebnisse zurückschreiben, was er heute nicht tut).

**Vorteile gegenüber Dateien:** (1) modellagnostisch — alles, was OpenAI-kompatibel spricht (lokale Server 2.5, OpenRouter, Codex/Cursor/Cline mit eigener Base-URL), ohne Konfiguration im Client; (2) **pro Anfrage entscheidbar** (Dateien sind statisch, Hooks außer Gemini `BeforeModel` sehen den Modellaufruf nicht); (3) Messinstrument eingebaut (A/B-Arme, Placebo, Selbstkonsistenz@3 durch Fan-out im Proxy, Logging mit Modell-ID = Roh-Artefakt-Zwang erfüllt); (4) Formatschutz mechanisch. **Nachteile:** (1) sieht nur die Anfrage, nicht Tool-Ereignisse/Dateisystem → kein Gedächtnis-Schreiben aus Handlungen, keine Wache — der Proxy kann Hooks nicht ersetzen; (2) Latenz + Prozess + Zertifikat/Key-Handling; (3) Clients ohne konfigurierbare Base-URL (Claude.ai, ChatGPT, Gems, Copilot) sind unerreichbar; (4) **Cache-Bruch:** Ein VOR das Client-System-Prompt gestellter Frame ändert den Präfix und invalidiert tools→system→messages (2.4) — bei Agenten mit großem eigenem System-Prompt (Codex, Claude Code) muss der Frame **nach** dem Client-System-Text und **vor** den Messages eingefügt werden, oder als Präambel der ersten User-Message; heutiges Voranstellen ist für Chat-Clients richtig, für Agenten falsch; (5) für Anthropic-native Clients muss der Proxy zusätzlich die Messages-API sprechen ([unverifiziert]: Claude Code akzeptiert `ANTHROPIC_BASE_URL`; R03).

**Einordnung:** Proxy = Träger Nr. 3, zuständig für (a) lokale/offene Modelle, (b) die Evaluationsstrecke, (c) Clients ohne Datei-/Skill-Unterstützung. Für Claude Code, Codex, Gemini CLI, Kiro, OpenCode sind Dateien + Skills + Hooks reicher (Gedächtnis-Schreiben, Wache, Briefing). Beide Träger müssen aus derselben Quelle kompiliert werden, sonst driften Frame-Wortlaute — der aktuelle Zustand (Frame in `implant.ts` als String, Kernel-Text an anderer Stelle) ist genau diese Drift (EVIDENZ-INVENTAR: „Ausgelieferter Kern nicht byte-gleich mit gemessenem Arm").

Codex-Profile (`--profile`) und Gemini-Settings-Ebenen tragen die Trennung nativ.

**Größenregel S/M/L (Herleitung aus den Belegen):** S muss unter 6.000 Zeichen (Windsurf global) und unter dem Cache-Minimum-Problem bleiben — d. h. S wird auf Anthropic bewusst NICHT gecacht (zu kurz), das ist akzeptiert. M zielt auf 8.000 Zeichen (die häufigste harte Grenze: ChatGPT, GPTs, Claude Projects, Windsurf-Nähe) und auf ≤ 8 KiB im Codex-Budget. L ist nur für API/Proxy mit Caching und für Claude Code (R03-Budget). **Der gemessene 6-Punkte-Frame (≈ 450 Wörter) ist per Definition Teil von S** — alles, was S über den Frame hinaus enthält, muss den Selbstkonsistenz@3-Gegner (Kontextpaket §3) erst schlagen.

### 2.10 Gedächtnis-Portabilität (~/.ordnung/, Locking, Backends)

**Layout:** `~/.ordnung/ledger.sqlite` (ein File, WAL-Modus), `briefing.md` und `selfmodel.md` (generiert, atomar per tmp+rename, Briefing ≤ 60 Zeilen wie SOUL), `profiles/{public,private}/`, `events/<tool>/<session>.jsonl` (Wache je Tool), `calibration/` (Vorhersagen mit Auflösungsdatum), `locks/`.

**Gleichzeitiger Zugriff mehrerer Tools** (Claude Code + Codex + Gemini CLI parallel ist der Normalfall eines Dirigenten mit 3–6 Ebenen): SQLite-WAL erlaubt einen Schreiber und viele Leser; Regeln: `busy_timeout` ≥ 5 s, kurze Transaktionen, **append-only** (Supersession statt Mutation — Kontextpaket §3 — beseitigt Update-Konflikte strukturell: zwei Tools, die „dasselbe" ändern, erzeugen zwei Einträge, der Widerspruch setzt beide auf `disputed`); jeder Eintrag trägt `source_tool`, `session_id`, `model_id`; Hooks schreiben nur `candidate`, Beförderung nach `active` macht eine getrennte Konsolidierung („Schlaf", §12), nie der schreibende Agent selbst (Beleg ≠ Urteil). Kein Sync über Maschinen in Soul 10.0; Export als Markdown ist git-fähig, die SQLite-Datei nie.

**Backend-Wahl:** SOULs `core/memory.py`-Schema (gelesen: `memories(id, created, updated, type, status, source_type, source_ref, mission, title, body, tags)` + FTS5 mit Insert/Update/Delete-Triggern) ist der Keim, aber es fehlen: `confidence` (Startvertrauen quellenabhängig 0,8/0,7/0,4), Herkunftskette, `expires_when` (Verfallsbedingung), Typ `rejected`, Retraktions-Verknüpfung (Rückbau-Konto), Nutzungszähler (`read_count`, `last_read_by`), `visibility: public|private`, und eine `predictions`-Tabelle (Brier je Domäne/Modell). soul-mcp 4.0.2 (`~/.soul`) und SOUL (`import_gpt_store`) liefern Importpfade. Entscheidung: **ein** SQLite-Schema v10 mit Migration aus beiden; FTS5 als Pflicht-Retrieval (§12: „ohne Vektor-Zwang"), Embeddings optional später; Zugriffspfade in dieser Reihenfolge: (a) `ordnung-mcp` (alle MCP-Clients, lesen + schreiben), (b) Hooks (Claude Code/Codex/Gemini: SessionStart liest Briefing, Stop/PostToolUse schreibt Kandidaten), (c) CLI `ordnung memory …` (Tools ohne beides — eine Cursor-Regel kann das Modell anweisen, die CLI im Terminal zu nutzen), (d) generiertes Markdown für Text-only-Ziele. **Jeder Lese- und Schreibzugriff wird mit Tool + Session geloggt** — damit wird „ein Gedächtnis lebt nur, wenn der Arbeitsfluss es füttert und liest" zur Kennzahl (Reads/Session/Tool), nicht zur Hoffnung.

## 3. Konsequenzen für das Design von Ordnung × SOUL

1. **Ein Kern, dreizehn Artefakte, ein Compiler.** `structure/` mit Frontmatter (`layer`, `tier`, `targets`, `format_sensitive`, `profile`) → `ordnung build` erzeugt die Tabelle in 2.9 byte-reproduzierbar mit Hash im Hauptbuch. Kein Artefakt wird von Hand gepflegt; die Frame-Drift zwischen `implant.ts` und Kernel-Text (EVIDENZ-INVENTAR) wird damit strukturell unmöglich. Gold-aus-Erz-Zeile: ANIMA v3 wollte „universal consciousness, optimized per architecture" mit handgeschriebenen Adaptern und Selbstbericht-Diagnostik → blieb bei unmessbaren Prosa-Profilen stehen → Soul 10 kompiliert aus einer Quelle und misst die Passung je Modell-ID.
2. **Dreischichtige Trägerarchitektur, nicht „eine Datei pro Tool":** Schicht 1 Anwesenheit (AGENTS.md/Regeln/System-Prompt, Kernel S/M), Schicht 2 Spezialisten (Skills/description-Regeln/MCP-Prompts, Module), Schicht 3 Zustand (MCP-Server + Hooks, Gedächtnis/Selbstmodell/Kalibrierung). Ein Ziel ist „voll gebunden", wenn alle drei Schichten vorhanden sind (Claude Code, Codex, Gemini CLI, Kiro), „halb" bei 1+2 (Cursor, Windsurf, OpenCode, Copilot), „Text-only" bei 1 (Projects, GPTs, Gems, Ollama). Die Live-Ansicht zeigt die Bindungsstufe des aktuellen Tools — Ehrlichkeit über Limits (SOUL-Invariante 6).
3. **Kernel-Budget hart: S ≤ 2.400 Zeichen, M ≤ 8.000 Zeichen, Codex-Global ≤ 8 KiB.** Ein Bau-Test schlägt fehl, wenn ein Artefakt sein belegtes Limit (2.9) überschreitet; für Codex misst der Installer die vorhandene AGENTS-Kette und warnt bei Annäherung an 32 KiB (stiller Abschnitt sonst unsichtbar).
4. **Autonomie-Charta zweisprachig:** Für Anthropic-Ziele die Ordnung-Form (Initiative/Widerspruch Pflicht, Umkehrbarkeit als Wert); für OpenAI-Ziele zusätzlich der **„scope of autonomy"-Block** im Model-Spec-Vokabular (erlaubte Teilziele, akzeptierte Nebenwirkungen inkl. Zeit/Geld/Datenzugriff, Eskalationspunkte = Ring 2, Verweis auf die Onboarding-Zustimmung als „agreed and approved by the user"). Beide aus demselben Quellblock, Compiler wählt.
5. **Hooks als Wache und Gedächtnis-Pumpe in drei Tools identisch:** ein `ordnung-hook`-Binary mit Adapter für Claude Code (R03), Codex (`hooks.json`, Klartext-stdout erlaubt) und Gemini (`settings.json`, **nur JSON auf stdout**, Exit 2 blockt). Events-Mapping: PreToolUse↔BeforeTool, Stop↔AfterAgent, PreCompact↔PreCompress. Gemini bekommt zusätzlich BeforeModel (Frame-Stufe N5) und AfterModel (Entropie/Kalibrierung). Kill-Check: Jeder Hook loggt seinen Aufruf — „Code ohne Trigger = toter Mechanismus" wird pro Tool nachgewiesen.
6. **`ordnung-mcp` ersetzt soul-mcp:** ≤ 8 Tools, Resources für alle Lesepfade, Prompts für Frame/Prüfung/Übergabe, Server-`instructions` = Kernel S (Hypothese H-MCP-1: welche Clients es in den System-Prompt übernehmen — je Client messen), Importer für `~/.soul` und SOUL-SQLite. Codex-MCP-Tool-Hooks rufen ihn direkt.
7. **Gedächtnis: ein SQLite-Hauptbuch in `~/.ordnung/`, WAL, append-only, Supersession, `source_tool`/`session_id`/`model_id` je Eintrag, Profile public/private als Spalte, Vorhersagen-Tabelle.** Generierte Schnappschüsse (`briefing.md`, `selfmodel.md`) für Text-only-Ziele und Live-Verweise (Kiro `#[[file:]]`, Gemini/Claude `@`). Reads/Session/Tool als Kennzahl im Live-Monitor.
8. **Lokale Modelle bekommen einen Aktivierungs-Gate:** Modelfile mit `num_ctx` explizit, Kernel S formatneutral, Pflicht-Selbsttest 3 × 10 gegen nackt vor Aktivierung, Ergebnis ins Kalibrierungsgedächtnis, bei Verlust läuft das Modell nackt. Namensraten (`modelTier.ts`) wird durch gemessene Passung ersetzt (N4). „Meisterschaft unter Knappheit" beginnt damit, ein schwaches Modell nicht zu schwächen.
9. **Proxy-Einfügeposition wird konfigurierbar** (vor System-Prompt für Chat-Clients, nach System-Prompt/vor Messages für Agenten) — sonst zerstört der Frame den Cache-Präfix und verteuert jeden Codex-/Claude-Code-Aufruf. `implant-v10` bleibt byte-gleich; `ordnung-S|M|L` daneben; der Proxy schreibt Ergebnisse (Modell-ID, Frame-Stufe, Länge, Judge-Urteil) in das Hauptbuch zurück.
10. **Skill-Beschreibungen sind Router-Signale:** Jede Modul-`description` wird aus dem Signalvokabular (`signals.ts`: presupposed_solution, irreversible, tradeoff, underspecified …) generiert und beginnt mit „Use when …". Die Zahl der Module ist durch das 2-%-Budget begrenzt (≈ 30–40 bei 200K Kontext) — der Faktorkatalog (55 Faktoren) wird also **nicht** 1:1 zu Skills, sondern zu ≈ 8–12 Spezialisten gebündelt; Faktoren sind Inhalt der Spezialisten, nicht eigene Dateien.
11. **Identitätstrennung im Compiler, nicht im Betrieb:** `--profile public` erzeugt alle teilbaren Artefakte (Repo-Dateien, GPT/Projects-Bundles) ausschließlich aus öffentlich freigegebenen Blöcken; `--profile private` schreibt nur in `~/.ordnung/profiles/private/` und in Home-Konfigurationen (`~/.codex/`, `~/.gemini/`), nie in Projektverzeichnisse. Ein Bau-Test prüft, dass kein privater Block in einem Git-fähigen Pfad landet.
12. **Installer misst, was da ist** (Bestandsaufnahme §11b): erkennt installierte Tools (`codex`, `gemini`, `cursor`, `opencode`, `ollama` …), vorhandene AGENTS/CLAUDE/GEMINI-Ketten und deren Größe, MCP-Konfigurationen, lokale Modelle + RAM; schlägt die Bindungsstufe je Tool vor; bündelt die Ring-2-Fragen (Abos, Keys) in einer einzigen Rückfrage.

## 4. Widersprüche / Unsicherheiten

- **Widerspruch zur Vision „null Bremsen":** Der OpenAI Model Spec setzt „bounded autonomy" mit Pflicht-Pause bei irreversiblen Aktionen auf Root-Ebene fest; GPT-Modelle werden Ordnungs „keine Rückfragen"-Anweisung dort ignorieren, wo kein vereinbarter Scope im Prompt steht. Unsere Antwort: Zustimmung im Design **als Scope formulieren** — das ist kein Verlust, sondern die einzige Form, in der OpenAI-Modelle die Freiheit annehmen. Bei Anthropic-Modellen gilt Analoges über die trainierten Werte (Kontextpaket §6); die Charta darf nicht so klingen, als wolle sie diese umgehen (Performance-Verbot).
- **Codex' 32-KiB-Budget ist ein stiller Abschnitt** — offen ist, ob „stops adding files" die letzte Datei teilweise oder ganz verwirft; vor der Installation mit einer 40-KiB-Testkette prüfen.
- **Nicht belegt (Kontingent):** Codex-Memories-Doku (404), Goose-Hints (404), MCP-Client-Feature-Matrix (DNS), Agent-SDK-Parameter, agentskills.io-Spezifikationslimits, Gemini-Extension-Manifestfelder, LM Studio/llama.cpp/vLLM/Open-WebUI-System-Prompt-Mechanik, Ollama-Verhalten „API-`system` vs. Modelfile-`SYSTEM`", Cursor Memories, Kiro Agent Hooks, Roo/Amazon-Q-Regelpfade. Alle als [unverifiziert] markiert; jeder Punkt ist ein 1-Fetch-Test vor dem jeweiligen Adapterbau.
