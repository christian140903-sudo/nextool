Case study

Anatomy of a phantom effect

I measure whether it really works — even when the result goes against me.

As of 8 October 2026 · raw data not yet published · Chriso puts the text into his own words and checks the sections “How the flaws were found” and “What was left after the fix” against the sources himself

Summary

In August 2026 I measured whether my own system prompt improves language models on the HumanEval coding benchmark. I registered +17.8 percentage points and withdrew them the same day, before the number left the project. From the stored answers only +15.6 can be recomputed — the difference is unexplained. After fixing the grader, +3.3 remained (p = 0.375) on runs that were still unequally instructed; the experiment could not be corrected, only discarded. Raw data not yet published.

The question

In August 2026 I was working on a system prompt that puts a fixed thinking frame in front of every request to a language model: six working instructions such as “reread the request as its author” or “challenge the prescribed path”. The hypothesis, which later turned out to be wrong: the frame makes answers better, regardless of the model.

Early comparisons in which a language model judged pairs of answers looked good. But judge verdicts on self-written tasks are the first thing a reviewer takes apart. So the next question: does the effect hold on someone else's benchmark, graded mechanically by someone else's tests?

The setup

  • Benchmark: HumanEval with its own tests, plus EvalPlus with stricter edge-case tests. Datasets pinned by hash, a sample of 30 of 164 tasks, fixed random seed.
  • Paired: arm A is the bare model, arm B the same model with the frame; same tasks, same run.
  • Models: the runs discussed here used two open models from the same family, gpt-oss-120b and gpt-oss-20b.
  • Fixed in advance: below 90 % complete answer pairs, a cell counts as “not measured” and gets no number. Before the second repeat run I committed a confirmation criterion to version control (11:57; the run followed at 12:25, on 28 August 2026).
  • Placebo arm (from 28 August 2026): factual text about ocean tides, matched to the length of the frame, without instruction words; a test checks this against a list of forbidden words and cross-checks that the same list does hit the real frame. Its runs stayed incomplete (19 and 26 of 30 each tasks) and therefore below the project's own completeness threshold.

On paper, a clean setup.

The first result

The first run on 27 August 2026 showed nothing: every confidence interval contained zero. The diagnosis found a cause. An outdated model list classified the larger model as “small”, and “small” forced a visible plan before the answer; some answers with the frame therefore contained no code at all.

After the fix the picture flipped. Three repeat runs on 28 August 2026 averaged +17.8 percentage points for the frame — the number I withdrew the same day. The criterion fixed in advance for the second run was missed, and I recorded it as missed. The overall impression stayed strong anyway, and the interim state of the incomplete placebo runs seemed to confirm it. On top came an explanation that sounded good: answers with the frame stuck to the required function signature. The placebo interim state and this explanation are withdrawn too.

How the flaws were found

The same day, an audit ran on the stored answer files only, without a single new model call. After that came a counter-check under a rule I had written down three days earlier: before any number can leave the project, two or three review agents are set on it with the job of finding errors. Who triggered the first audit is not documented in my records.

First flaw: the grader took the first code block

My own grading code pulled the first Markdown code block out of an answer before running someone else's tests. The bare model, however, often wrote several blocks; the model with the frame almost never did. Typical case: the first block held a formula as pseudocode, the actual solution came in the second. The formula got graded. Taking the block with the required function signature instead rescues 36 answers and breaks none, most of them in the bare arm. This flaw was fixable.

Second flaw: only one arm got a format instruction

The night before, a format guard had been added to the connection that injected the frame. For mechanically graded requests it added one sentence: “Nothing at all may stand outside the deliverable … Match the requested output format exactly.” It was triggered by the key the test harness used for the framed arm. Arm B got this sentence, arm A no format instruction at all. The format guard itself was built and tested; it simply acted on one side only. This flaw is in the runs themselves and could not be fixed afterwards. The counter-check found it, not I.

That is how the phantom effect is explained as of today: the framed arm almost always wrote exactly one block, and only it had received an instruction that amounts to exactly that. The grader turned “one block” into “correct”. A run with the same instruction in both arms, which would test the role of the format instruction separately, is missing.

What was left after the fix

With correct code extraction, the mean over six measurements was a difference of +3.3 (p = 0.375); the confidence intervals contain zero for both models. These runs were still unequally instructed, though — the experiment could not be corrected, only discarded. Raw data not yet published.

Against the filler text, no consistent lead was left after the fix: below on one model, above on the other — on placebo runs that stayed incomplete. The difference in signature adherence shrank to a fraction as well; the explanation “sticks to the signature” is withdrawn. The benchmark had largely measured answer formatting, not correctness.

What I cannot explain

The registered and withdrawn number (+17.8 percentage points) cannot be recomputed exactly from the stored answers. The unchanged grader gives +15.6 on the same files, confirmed by two independent calculations. I do not know where the difference comes from. I state it anyway, because a case study about measurement errors would otherwise hide one itself.

The second phantom effect: length instead of quality

The earlier comparisons had been scored by an AI judge. The audit showed that this judge mostly picked the longer answer. In a separate recalculation from the stored raw verdicts, the longer answer wins 71.0 % of the comparisons. Whether the judge rewards length or the longer answers really were better has not been separated. The advantages measured with this judge therefore no longer count as evidence; I withdrew them. Raw data not yet published.

How to check whether an AI improvement is real

Five rules for teams that introduce prompts, skills or agents:

  1. Measure against the same amount of text, not against nothing. A version of equal length without instructions is the fair zero point. Measuring only against “nothing” credits a plain context effect to your instructions.
  2. Verify equal treatment on the wire. Compare the requests both variants actually send, byte for byte. A guard layer, a flag, a key: anything that reaches only one side gets measured along with it.
  3. Test the grader as hard as the candidate. Read the answers that were marked wrong yourself. The code-block flaw sat in the files all along; it only became visible when someone read the answers instead of just the hit rate.
  4. Fix thresholds in advance, keep the raw data. Version criteria and predictions before the data, save every raw answer as a file. The flaws could be found without a new model call because everything was on disk.
  5. Before any number goes out, a second instance whose job is “find the error”. Whoever built the experiment does not see their own assumption. Here the counter-check found the worst flaw, not the author of the experiment.

For a team that maintains skills in its own repository, that means in practice: every change to a skill runs against a fixed task list, against the old version and against an equally long blank version; checks are mechanical wherever possible, and the result is versioned with the commit.

What came out of it

  • A lock with a withdrawal list: a lock file and a machine-readable list of which numbers are locked or withdrawn — created on 28 August 2026, not yet in a public repository.
  • Measurement rules: form is the most dangerous confounder, so harden extraction and grading against length and format; prove equal treatment on the wire instead of assuming it in code; measure your own noise first — an unchanged arm varied by up to 16.7 percentage points between two runs (still measured with the faulty extraction).
  • Follow-up measurements on this pattern: no AI judge, filler text as the zero point, thresholds in advance. The fact-check of this case study found that in one of them the filler text was only a little over half as long as the frame — so the first rule was not met there either. Their results are not yet published in prepared form.
  • A product decision: the premise “one fixed frame that helps every model on every task” is recorded in the project as refuted by its own data.

The same idea sits in two small tools from July: postcondition-mcp checks independently, after an agent action, whether the world really changed; behaviorlock compares agent behaviour before and after a model or prompt change. Success is not claimed but checked against an observable state.

What this case study does not show

  • The raw data of the HumanEval runs, the lock file and the withdrawal list are stored locally and not published. The numbers on this page cannot yet be checked from outside.
  • Small sample, two open models from the same family. The experiment as a whole was not pre-registered; only the completeness rule and the criterion for the second run were fixed in advance. The runs were re-checks after repairs.
  • The harness's interval method was too narrow because it conditioned on the discordant pairs; correct intervals would be wider. The p-value comes from a sign test that treats the runs as independent although they share the same tasks — it is correspondingly weak.
  • The placebo runs stayed incomplete.
  • Why the registered number cannot be recomputed is open. Who triggered the first audit is not documented.
