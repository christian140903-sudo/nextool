soul-mcp

npm · version 4.0.2 · MIT · as of 8 October 2026

Problem: a coding agent that remembers things for weeks can also remember injected instructions — and later no longer knows where a memory came from.

What it does: a memory server for MCP clients (such as Claude Code) that quarantines injected instructions and records provenance. Local, one SQLite file, 23 MCP tools.

Measured: plain runtime attachment without skills showed no quality gain on 20 tasks at 2.7× cost; the skill effect is unmeasured — that is what my own inventory says. Raw artefacts not yet published.

Limits

No external user documented; my own use is self-reported. Last npm release on 14 August 2026, open Dependabot updates. No evidence that it improves the quality of model answers.

Verification tools for agents

Separate packages, built in July 2026. They are not integrated with each other; there is no shared integration test. Only postcondition-mcp checks whether an agent did what it reports — behaviorlock and agent-invariants compare runs against rules, proofspec compares claims against evidence.

postcondition-mcp

npm · version 0.1.0 · MIT · as of 8 October 2026

Problem: a tool reports “success”. Whether the world actually changed is a different question.

What it does: postcondition-mcp checks whether the world changed, not whether the agent said so. The intended result is declared up front; narrow, read-only verifiers (file, HTTP GET, Git, npm) observe it; the verdict is satisfied, violated or unknown. I triggered the failure case: a tampered ledger reports itself as invalid.

Limits

A young project, built in one evening, with no external users. The local hash chain detects changes but is not a signed notarisation. Anything a human or agent attests stays labelled as self-attested.

behaviorlock

GitHub release · version 0.1.0 · not on npm · MIT · as of 8 October 2026

Problem: after a model or prompt change, a skill silently produces something different.

What it does: a drift gate for skills after model updates. It compares runs before and after a change against fixed, deterministic rules — no judge model — and reports compatible, drifted or unknown. One external project references it.

Limits

It detects drift; it does not prevent it. Only what is captured as a scenario and rule gets checked; weak coverage creates false confidence. The external reference is a mention in a young one-person repository, not a user report. Overlaps with agent-invariants.

agent-invariants

GitHub release · not on npm · MIT · as of 8 October 2026

Problem: after a refactor, an agent calls a payment tool without approval, keeps working after a stop, or reports “done” without an observed outcome.

What it does: checks recorded agent runs against explicit operating rules (approval, stop, retry limits, ordering) and compares a known baseline with a changed candidate.

Limits

Does not grade answer text and is not an enforcement point: it reports rule violations in a run; it does not stop an action. Overlaps with behaviorlock.

proofspec

GitHub release · version 0.1.0 · not on npm · MIT · as of 8 October 2026

Do not install from npm

The npm package named proofspec belongs to a different project. Do not run npx proofspec; clone the repository instead.

Problem: a README, a release or an agent's completion message claims something — nobody checks whether it still holds.

What it does: turns the important claims into versioned checks with evidence policies and dependencies; a CI gate fails when a required claim is not backed. Observation runs through postcondition-mcp's narrow verifiers.

Limits

A satisfied verifier proves only its configured observation, not the broadest reading of the sentence. No arbitrary shell commands; manual evidence stays “unknown”. The local receipt chain detects changes but is not a signed log. A young project with no external users.

Measurement and evals

What I measured about the effect of my own work — including when it went against me.

  • A phantom effect, withdrawn the same day. My own system prompt seemed to help a lot on a public coding benchmark. But the grader took the first code block of each answer, and only one arm had been given a format instruction. I withdrew the number before it left the project. → Case study “Anatomy of a phantom effect”
  • A null result. Plain runtime attachment of soul-mcp without skills showed no quality gain on 20 tasks at 2.7× cost; the skill effect is unmeasured. One run, one model, descriptive. The protocol with its hash pinning, the statistics script and the tasks with their verifiers are public in the soul-mcp repository; the raw artefacts of the run are not yet.
  • The longer answer wins. In earlier comparisons scored by an AI judge, the longer answer won 71.0 % of the comparisons (a separate recalculation from the raw data). Whether the judge rewards length or the longer answers were better is open; I withdrew the advantages measured with that judge. Raw data not yet published.
Limits

Until the raw data are published, none of these measured numbers can be checked from outside — only the method and, for the null result, the protocol and tasks.
